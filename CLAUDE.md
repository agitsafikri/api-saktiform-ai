## Architecture Overview

This is a **multi-tenant conversational commerce platform** — WhatsApp-based AI chatbots combined with e-commerce order management. All resources are scoped to a `Workspace` (tenant).

### Layer Structure

```
com.saktiform.api/
├── configuration/   # Security (JWT), MinIO, WebSocket, Swagger config
├── controller/      # REST endpoints
├── entity/          # JPA entities (PostgreSQL)
├── model/           # DTOs and request/response objects (sub-packages: chat/, order/, product/, etc.)
├── repository/      # Spring Data JPA repositories
├── service/         # Business logic
│   ├── chat/        # Conversation, WhatsApp messaging, WebSocket
│   │   └── bot/     # AI bot orchestration (OpenAI/Gemini/Qdrant)
│   └── order/       # Order lifecycle, event listeners
├── util/            # Helpers (image processing, phone number, seeding)
└── validators/      # Custom JSR-303 validators
```

### Multi-Tenancy

Every resource belongs to a `Workspace`. Repositories enforce isolation with native SQL queries that join through `produk.id_workspace`. Controllers receive `workspaceId` as a query/path parameter and pass it down through the service layer — there is no thread-local tenant context.

### Security

JWT-based, stateless. `JwtAuthenticationFilter` (extends `OncePerRequestFilter`) validates bearer tokens before `UsernamePasswordAuthenticationFilter`. Tokens are HS256-signed with 24-hour expiry, generated by `JwtManager`.

Public endpoints (no auth): `/whatsapp/*/webhook`, `/produk/checkout/**`, `/order/create/**`, `/location/**`, `/account/login`, `/media/**`, `/swagger-ui/**`, `/v3/api-docs/**`.

### Bot / AI Pipeline

Incoming WhatsApp messages flow:

```
WhatsappController (POST /whatsapp/webhook)
  → WhatsappMessageHandler.handleMessagePayload()
    → saves Chat entity, updates Conversation (unread count, last message)
    → publishes ChatAsyncEvent
  → BotIncomingChatListener (@EventListener)
  → BotOrchestratorService.onIncomingChat()
    → checks isOrderMessage() — if true, routes to sendConfirmationMessage()
    → BotDecisionService.shouldBotReply() — checks if workspace bot is enabled
    → BotDelayManager.debounce() — debounces per conversation (cancels prior pending tasks)
    → BotService.handleBotReply()
```

`BotService.handleBotReply()` uses a three-tier fallback:
1. Rule-based reply
2. RAG via Qdrant vector DB (`ragBasedReply()`)
3. Direct LLM fallback

LLM provider is selected by `AiClientFactory` (reads `AI_KEY` from `AppConfig` entity). Supports `OpenAiLlmService` (official Java SDK) and `GeminiLlmService` (REST). Qdrant holds two collections: `knowledge_base` (product/workspace context) and `user_tendencies` (per-user behavior).

Order confirmation is detected by regex in `BotService`:
```
"Halo, saya sudah melakukan pemesanan (.*?), atas nama (.*?)\. Mohon segera diproses ya .*"
```

### Order Flow

`OrderController POST /order/create` → `OrderOrchestrationService` → publishes `OrderCreatedEvent` via `ApplicationEventPublisher` → `OrderEventListener` (async, runs after transaction commit via `TransactionPhase.AFTER_COMMIT`) → sends WhatsApp follow-up message using `MessageTemplateService` template + `WhatsappClientHelper`.

### WebSocket / Real-time

STOMP over SockJS at `/ws`. Simple broker on `/topic`. `ChatEventPublisher` publishes `ConversationEvent` objects to topic destinations. `ChatWebSocketEventListener` handles connect/disconnect. Heartbeat is 10 seconds; max message size 512 KB.

### Async Processing

`@EnableAsync` is active globally. Bot message handling and order event processing run on the async executor. `BotDelayManager` uses a `ScheduledExecutorService` (thread pool = `max(4, CPU cores * 2)`) to debounce bot responses per `conversationId`.

### External Services

All base URLs are environment-variable-driven:

| Service | Env Var | Default |
|---|---|---|
| WhatsApp multi-device API | `WHATSAPP_MULTIDEVICE_API_URL` | `http://103.49.239.5:3000` |
| MinIO | `MINIO_URL`, `MINIO_ACCESS_KEY`, `MINIO_SECRET_KEY` | see `application.properties` |
| Qdrant gRPC | `QDRANT_HOST`, `QDRANT_PORT` | — |
| OpenAI | `OPENAI_API_KEY` | stored in `AppConfig` entity |
| Gemini | `GEMINI_API_KEY` | stored in `AppConfig` entity |
| Checkout frontend | `SAKTIFORM_CHECKOUT_URL` | `http://103.49.239.5:3500` |

### Database

PostgreSQL. Schema auto-updates via `spring.jpa.hibernate.ddl-auto=update`. HikariCP pool (max 20, min idle 5). `InitializerSeeder` (`@PostConstruct`) seeds superadmin and initial workspace data on startup. `OrderSequence` entity manages per-workspace order number sequences.

### Key Entities

- `Workspace` — top-level tenant; all other entities join to it
- `Account` — user with role (SUPERADMIN / ADMIN / AGENT), belongs to one or more Workspaces
- `Produk` — product with variants (`AtributProduk`), extras (`ProdukEkstra`), images (`GambarProduk`), payments (`ProdukPembayaran`)
- `Order` / `AbandonedOrder` / `OrderHistory` — order lifecycle
- `Conversation` / `Chat` — WhatsApp conversation thread and individual messages
- `Contact` — WhatsApp contact (phone number) scoped to Workspace
- `AppConfig` — per-workspace key-value config (stores AI keys, bot settings)
- `Domain` — custom domain mappings per Workspace
- `WhatsappBusinessApi` — registered WhatsApp instance per Workspace

### Response Conventions

All REST endpoints return `RestResponse<T>`. Validation errors return `ErrorResponse` with a list of `ErrorDto`. Use `MapperHelper` for DTO mapping instead of inline field assignment.
