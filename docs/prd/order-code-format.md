# PRD — Order Code Format (`generateOrderCode`)

| Field | Value |
|---|---|
| Feature name | Order Code Format Update |
| Component | `OrderService.generateOrderCode()` |
| Status | Implemented |
| Scope | Global (order codes are not workspace-scoped today) |
| Author | — |
| Last updated | 2026-06-29 |

> This PRD covers only the change to how new order codes are generated. The open questions raised during drafting have been answered and are recorded under **Resolved Decisions**; the sections below reflect those answers.

---

## 1. Background

Every `Order` is assigned a human-readable `order_code` at creation time. It is generated by `OrderService.generateOrderCode()` and used across the system for search and display (e.g. `OrderRepository` and `ConversationRepository` filter on `order_code` via `ILIKE`).

The per-month running number is backed by the `OrderSequence` entity (table `order_sequence`): a row per month whose `seqValue` is incremented for each new order in that month.

**Current behavior** (`OrderService.generateOrderCode()`):
- Month key: `YearMonth.now()` formatted as `yyyyMM` (6 digits, e.g. `202606`).
- Sequence: looks up `OrderSequence` by the `yyyyMM` key, starting at `0`, increments by 1, saves.
- Output format: `String.format("ORD-%s-%05d", yyyyMM, nextNumber)`.
- Example produced today: `ORD-202606-00001`.

---

## 2. Problem Statement

The business wants order codes to be a compact, fixed-length **9-digit numeric** string in the form **`YYMMXXXXX`**, where:
- `YY` = 2-digit year,
- `MM` = 2-digit month,
- `XXXXX` = 5-digit running sequence that resets each month.

The current format (`ORD-202606-00001`) is 16 characters, includes a prefix and separators, and uses a 4-digit year. It does not match the desired 9-digit numeric layout.

---

## 3. Goals

- Change `generateOrderCode()` to produce a 9-character code `YYMMXXXXX`.
- Keep the monthly-sequence behavior (sequence is per calendar month).
- Keep generation safe under concurrent order creation (no duplicate codes within a month).
- Change only the code-generation logic; do not alter unrelated order behavior.

### Non-Goals
- Migrating or rewriting `order_code` values on existing historical orders.
- Adding a workspace component to the order code (it remains global unless decided otherwise — see Open Questions).
- Changing how `order_code` is searched/displayed elsewhere.

---

## 4. Scope

### Included
- Update the output format of `OrderService.generateOrderCode()` to `YYMMXXXXX` (numeric only, no prefix).
- Use a 2-digit year (`YY`) and 2-digit month (`MM`), derived from the **Asia/Jakarta** timezone.
- Use a minimum-5-digit, zero-padded, per-month sequence (`XXXXX`) that grows beyond 5 digits if it exceeds 99,999 (no cap).
- Keep the internal `OrderSequence` key as `yyyyMM` — only the displayed format changes.

### Not Included
- Back-filling or transforming existing `order_code` values.
- Any schema change beyond what the sequence mechanism already provides (see Data Model).
- Validation/parsing utilities for the new format (unless requested).

---

## 5. Functional Requirements

| ID | Requirement |
|---|---|
| FR-1 | A newly created order MUST receive a numeric `order_code` of `YYMMXXXXX` — 9 characters while the monthly sequence is ≤ 99,999. Beyond that, the sequence grows to 6+ digits (no cap), so the code may exceed 9 characters. |
| FR-2 | The first 2 characters MUST be the 2-digit year of the creation month (`YY`). |
| FR-3 | The next 2 characters MUST be the 2-digit, zero-padded month (`MM`, `01`–`12`). |
| FR-4 | The last 5 characters MUST be the per-month sequence, zero-padded to 5 digits (`XXXXX`). |
| FR-5 | The sequence MUST start at `1` for the first order of a given month and increment by 1 per order. |
| FR-6 | The sequence MUST be independent per calendar month (a new month begins a new sequence). |
| FR-7 | Concurrent order creation within the same month MUST NOT produce duplicate codes. |
| FR-8 | Existing historical `order_code` values MUST remain unchanged. |

Example: the first order in June 2026 → `260600001`; the 42nd → `260600042`.

---

## 6. Non-Functional Requirements

| ID | Requirement |
|---|---|
| NFR-1 | The change is confined to `generateOrderCode()` (and, if required, the sequence key handling); no other order logic changes. |
| NFR-2 | Generation must be concurrency-safe and consistent with the existing `OrderSequence` persistence approach. |
| NFR-3 | No regression to order creation flow, search (`ILIKE` on `order_code`), or display. |
| NFR-4 | Backward compatible: old-format codes and new-format codes coexist; consumers treat `order_code` as an opaque string. |

---

## 7. Current vs Target

| Aspect | Current | Target |
|---|---|---|
| Year | 4-digit (`2026`) | 2-digit (`26`) |
| Month | 2-digit (`06`) | 2-digit (`06`) |
| Prefix / separators | `ORD-` … `-` | none |
| Sequence | 5-digit, per month | 5-digit, per month (unchanged) |
| Length | 16 chars | 9 chars |
| Example | `ORD-202606-00001` | `260600001` |

---

## 8. Data Model Changes (conceptual)

- No new tables or columns are required; the `OrderSequence` table already tracks a per-month counter.
- **Decision (resolved):** keep the internal `OrderSequence` key as `yyyyMM` (e.g. `202606`) unchanged. Only the *displayed* output format changes (2-digit year). This preserves the current month's running counter and avoids century ambiguity in the key.
- No change to the `Order` entity (`order_code` stays a `String`).

---

## 9. Acceptance Criteria

- Given today is in June 2026 and no order exists this month, when an order is created, then its `order_code` is `260600001`.
- Given N orders already exist for the current month, when another order is created, then its sequence is the next integer, zero-padded to 5 digits, prefixed by `YYMM`.
- Given the month rolls over, when the first order of the new month is created, then the sequence restarts at `00001` under the new `YYMM`.
- Given two orders are created concurrently in the same month, then they receive two distinct codes (no duplicates).
- Given orders created before this change, then their existing `order_code` values are unchanged.

---

## 10. Edge Cases

- **Sequence overflow (> 99,999 in one month):** allowed — the sequence keeps incrementing and grows to 6+ digits (no cap), so the code exceeds 9 characters past the 99,999th order.
- **Mid-month cutover:** because the internal key stays `yyyyMM`, the first new-format code continues from the current counter value (e.g. existing `seqValue = 42` → next code `260600043`) rather than restarting. Accepted.
- **Year boundary:** December → January correctly changes both `YY` and `MM` because the key is derived from the current `YearMonth` in Asia/Jakarta.
- **Global vs per-workspace uniqueness:** the code has no workspace segment; it is unique per month globally, not per workspace. Accepted.
- **Timezone:** the year/month is derived from the **Asia/Jakarta** timezone (not the JVM default), so the month boundary is fixed regardless of server zone.

---

## 11. Resolved Decisions

All questions below have been answered by the product owner (answers inline) and reflected in the sections above.

1. **Sequence key strategy** — Should the `OrderSequence` key remain `yyyyMM` (Option a, preserves the current month's running counter and avoids century collisions) or switch to `yyMM` (Option b, resets the current month's counter)? Recommendation: Option (a) — change only the displayed format, keep the internal key as `yyyyMM`. Answer: only displayed format
2. **Overflow beyond 99,999/month** — What should happen if a month exceeds 99,999 orders? (e.g. allow the sequence to grow to 6+ digits and exceed 9 total chars, hard-cap, or treat as out of scope because volume is far below this.) answer : auto increment bebas (no cap), add digit when overflow
3. **Global vs per-workspace** — The code is currently global (the sequence is not scoped to a workspace). The `YYMMXXXXX` format has no workspace component. Confirm order codes should remain globally sequenced, or whether per-workspace sequencing/uniqueness is required. answer: global
4. **Timezone for the month boundary** — Should the year/month be derived from a specific timezone (e.g. Asia/Jakarta) rather than the JVM default, to avoid month-boundary drift? answer : fixed timezone, Asia/Jakarta
5. **Numeric-only guarantee** — Confirm the desired output is purely numeric (no prefix at all), so downstream consumers relying on the old `ORD-` prefix (if any) are checked. answer: numeric only
